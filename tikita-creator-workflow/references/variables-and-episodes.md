# 變數、章節
> 「官方限制」與章節的欄位、切換條件、進行模式是官方規則，其餘是這套工作流的做法。

# 變數
前七節是每部作品都用得到的；第八節只有模擬器類的作品才需要。

## 一、先決定要哪幾個變數
1. 整部作品最多 10 個。只記對話中會變、而且模型之後要回頭查的值；不必填滿。
2. 常見的種類，挑作品需要的：
   - 時間地點：回覆序號、日期時間、所在的地方。序號每則加 1，可以當其他規則的節拍。
   - 玩家狀態：身分、等級、目前的設定。
   - 帳本：錢、資源、待結算的收入。
   - 身上與住處：衣著、配件、身體狀態、持有物、住在哪。
   - 對象格：會反覆出現的重要對象，一格一人，多行。
   - 名冊：其他認識的人，一人一行。
   - 隱藏資料：只給模型看、玩家看不到的底細。
   - 約定清單：答應了還沒做完的事。
3. 同一個主體的幾件事併成一個多行文字變數，一行一件事，不要一件事開一個變數。
4. 名稱用中性英文加編號（Time、Score、Route1…），避免多語言與大小寫衝突。要用範圍說明或狀態面板量表的值（好感、信任、體力）用數字型，其餘用文字型最穩。
5. 數量在遊戲中才決定的實體（可領取 1～5 個的對象），變數不能在遊戲中新增，兩種做法擇一：
   - 預留格：一個數字變數 `Count` 加 N 個格子變數（沒用的預設「未領取」），狀態面板用 `{{#gte Count k}}` 決定顯示哪幾格。每個實體可有獨立卡片，但吃掉 N+1 個變數。
   - 單一清單變數：一個文字變數，每個實體一行，上限寫在說明裡，狀態面板用 `white-space:pre-line` 顯示。只用 1 個變數，但狀態面板無法對每個實體做獨立進度條。
   實體由模型依規則生成，屬於 NPC，不另建角色卡；領取條件與上限檢查寫進作品設定；生成規則放在生成當下會載入的地方（抽選或領取的那一章；沒有章節時放設定集）。

新開變數時的判準只有一個：這個值會變，而且之後有人要回頭查。兩個條件少一個就不開。使用者已經做好的變數不照這條刪：規則做不到就改寫規則，覺得用不到就列出來問他。菜單、價目這種不會變的寫進作品設定；天氣、氣氛這種當場寫就好的不用記；外貌與經歷在角色卡。

## 二、一個變數的說明怎麼寫（規格）
說明是模型更新這個變數時唯一的依據，也是使用者在 Studio 裡要回頭讀的東西。固定寫成下面的順序，不加別的段落：
1. **【用途】** 一句話：這個變數記什麼。
2. **【樣子】** 先講幾行與換行的寫法，接著直接放整個變數的版型，一行一行照實際的樣子排，emoji 只出現在這裡。玩家自己決定的欄位用欄位名（店名、暱稱），不放具體例子，模型會照抄。
3. **【每一行】** 有序列表，第 N 項對應版型的第 N 行。每一項把這一行的「放什麼、能填哪些值、什麼時候改」寫在一起，最多三句。格式和更新不要拆成兩段。
4. **跨行的規則塊**：只有一套規則同時管好幾行、或管整個變數時才另開一塊（例如【好感】【階段】【揭露】【收入與結算】），每塊用有序列表，一個變數最多四塊。

寫的時候守這幾條：
1. 列點一律用有序列表。
2. 例子只放在不看例子就會寫錯的那一行，用「例：「…」」接在該項後面；其他行靠版型就夠。
3. 不寫「{{user}} 第一則回應說明時照寫，其餘寫未設定」這類開場句。預設值本身已經是「未設定」，玩家說了模型自然會填。
4. 不寫「第 N 行：」這種前綴，序號就是行號。
5. 永遠寫目前的總值，不寫「+1」這類增減量；複合文字變數整串改寫。
6. 規則直接寫在這個變數的說明裡，不要只寫「見某角色卡」，更新時模型不一定去讀。
7. 一次性事件用「進程」記錄，只增不減；想隱晦就用數字標記，對應表放說明裡。
8. 狀態面板靠固定順序與全形寬度截取的那一行，欄位清單寫死，不能讓模型改動。
9. 只有一種開局時，初始值就是變數的預設值；有多種開局時，預設值放最常用的那個，其他開局的差異寫在開局章節的私設。預設值只在新聊天套用，舊對話不會重設，要開新對話測試。

**範例（虛構，改寫前後）**
改寫前，每一行都是一長句，同一行的規則還拆在【格式】和【更新】兩處：
```
第3行：🏠 店租：寫月租金額與繳款日，並註明目前是已繳還是逾期，例如「🏠 店租：18,000 元｜每月 5 日｜已繳」。
…
【更新】
- 店租過了繳款日還沒繳就改成逾期，付清後改回已繳。
```
改寫後：
```
【用途】{{user}} 這間店的錢、食材、店租，和答應了還沒做完的事。
【樣子】固定四行，用真正的換行分隔，不要使用\ n：
💰 現金 N 元｜今日營收 N 元
🥬 食材：…
🏠 店租：月租 N 元｜每月 D 日繳｜繳款狀態
📌 約定：…
【每一行】
1. 都寫目前的總值。客人結帳的那一則加進現金和今日營收，進貨、繳租的那一則從現金扣。日期換到隔天時今日營收歸零。
2. 只寫快用完和已經用完的食材，用「、」隔開，都夠時寫「充足」。用掉最後一份的那一則寫進來，進貨後拿掉。
3. 繳款狀態寫「剩 N 天」或「逾期」。日期每換一天把 N 減 1；到 0 的那一則還沒付就改成逾期；付清的那一則改回「剩 30 天」。
4. 一筆寫成「對象：內容（期限）」，用「；」隔開，最多五筆，沒有時寫「無」。例：「房東：補繳店租（3月12日）」。答應的那一則加上，完成、取消或過期的那一則刪掉。
```

### 數字變數怎麼寫
數字變數（好感、信任、體力）的說明短，態度的變化寫在「範圍說明」。
1. 說明寫兩塊：【用途】一句；【規則】用有序列表寫什麼事件加減多少、單則上限。
2. 範圍說明用有序列表，一個區間一項，寫這個區間裡他對 {{user}} 的感受與傾向。留白的話只有數字在動，態度不會變。
3. 最小值、最大值、起始值填在各自的欄位，不寫進說明。

範例（虛構）：
```
名稱 Trust｜數字｜最小 0｜最大 100｜起始 10
說明：
【用途】{{char1}} 對 {{user}} 的信任。
【規則】
1. 他在場時每則檢查：{{user}} 守住答應的事 +2；替他擋下麻煩 +4；說謊被他發現 -6。
2. 一則回覆合計最多 +4、-6，同一個理由只算一次。
範圍說明：
1. 0～29：對 {{user}} 還有戒心，只想把該談的事談完。
2. 30～69：覺得 {{user}} 可以相處，會想多留一會。
3. 70～100：把 {{user}} 當成自己人，遇到事情會先想到 {{user}}。
```
一個對象同時要記階段、心聲這些文字時，改用多行文字變數，好感寫成其中一行。

## 三、讓模型做對的規則（實測）
1. **用事件觸發，不寫機率**：「人數越高越可能有新角色」模型看不出什麼時候該做。改成看得到的事件：升級的那一場、上榜的那一場、回覆序號個位數是 0 的那一則。
2. **要定期發生的事，綁在每則都會更新的計數上**：有回覆序號時，用它的個位數當節拍最穩。兩件定期的事用不同的數字錯開（0 來新面孔、5 推限時活動）。
3. **抄，不要搬**：一份資料要在兩個變數之間出現時，讓一邊永遠留著完整的一份，另一邊照抄，用「（已揭露）」這類記號標狀態。「移過去再從這裡刪掉、換回來再搬回去」，弱的模型很容易漏一步。
4. **要數次數的規則，給它一個計數的位置**：「第一次輕、第二次中、第三次重」要有一格「罰過 N 次」，否則沒人在數。
5. **格式欄位不要放類型例子**：名冊欄位寫「觀眾類型，例如榜一、黑粉」，模型會把類型當成名字用。
6. **讓既有角色讓出戲份**：規則寫明每場只讓名單裡的幾位出現，並要求每場有一位第一次出現的人做出讓人記得的事，新角色才推得出來。
7. **會被忘記的事要有地方記**：約定、欠款、對方握有的東西、失去的記憶，沒有欄位的話模型過幾則就忘。

## 四、好感與關係階段
越簡單越好，只留模型記得住的。
1. **好感**是一個數字。說明裡寫什麼事會加、什麼事會減，各給一個固定的量，並設一則回覆的加減上限。對方在場的那一則才檢查。好漲還是難漲照角色的性格定。
2. **範圍說明**寫每個區間他對 {{user}} 的感受與傾向，區間寫成心境，不寫成關係。
3. **好感高代表在意，不代表他會把事情說出來**。他知道什麼、什麼條件才說，照角色卡的「認知範圍」。
4. **關係階段需要才設**，另立一行。用看得見的事實命名（「還沒認定」「認定之後」），和角色卡「與 {{user}}」底下的小節用同一個名字，模型靠這一行知道現在演哪一面。它記的是目前的關係，不是劇情的進度：判定寫一件看得見的事，一次最多變一階，不排成一串步驟。
5. 階段可以寫成「階段（他的心意）」：括號是參考，改括號不算升階。單方面的暗戀、債務這類關係寫在括號裡；爭執暫時疏遠時維持原階段，括號寫「保持距離」加心意，和好後改回。

## 五、常用的行
### 約定清單
1. 放在玩家狀態變數的最後一行，一筆寫成「對象：內容（期限）」，用「；」隔開，設上限（五筆）。
2. 答應的那一則加上；完成、取消或過期的那一則刪掉；到期當天對方會來提。
### 身上與住處
1. 一行一件事，順序照玩家看的習慣：住處、衣著、配件、身體、運作中的設備、全部的設備。
2. 「運作中」和「全部」分兩行：前者只列此刻在動的與狀態，後者只列名稱。混成一行會又長又難更新。
3. 身體那一行除了當下的狀態，也記會一直留著的東西（痕跡、失去的記憶），寫明留到什麼時候。
4. 住處帶繳租日與狀態（剩 N 天、逾期），日期每換一天把 N 減 1，房租的壓力才會自己出現。

## 六、接上作品設定、狀態面板與測試
變數寫完還有三件事，照順序做：
1. **作品設定放一句更新總則**。官方說明寫作品設定裡要有更新指示，AI 才會正確更新變數，所以在作品設定的「變數」一節放這一句：「每則回覆結尾檢查所有變數，照各變數的說明更新，寫目前的總值。」細則留在各變數的說明，作品設定只放這一句，不重複寫每個變數的規則。有作品沒寫這句也會更新，但各模型表現不一，寫上最穩。
2. **狀態面板對應每個變數**：
   - 要給玩家看的變數各放一格 `{{名稱}}`；多行文字變數的那一格加 `white-space:pre-line`。
   - 只給模型看的變數（隱藏底細）不放進自訂狀態面板就看不到。基本模式會列出全部變數，有隱藏資料時要用自訂 HTML。
   - 變數的行數改了，回頭檢查那一格會不會超過 300px。
3. **請使用者用便宜的模型開新對話測十則**（我沒辦法自己開聊天室），請他看五件事：格式有沒有跑掉、序號有沒有每則加一、數字有沒有照規則動、新角色有沒有出來、同一個暱稱前後有沒有一致。預設值只在新聊天套用，舊對話看不出變更。

## 七、官方限制
1. 變數在「章節」步驟建立。整部作品最多 10 個，只建立對話中實際會改變的值。數值由 AI 依對話內容自動更新。
2. 類型有數字、文字、布林值、列舉；畫面只能選文字與數字，布林與列舉只有用 MCP 建立才能指定，畫面上是灰色。
3. 上限：名稱 10 字、不含空格（狀態面板以 `{{名稱}}` 呼叫，畫面標籤可在 HTML 另外加空格）；說明 5,000 字；範圍說明 5,000 字；起始值 200 字。四者都計入作品總字數 30,000。
4. 數字變數可設最小值、最大值與「範圍說明」：角色在各數字區間的樣子。留白時只有數值變動，態度不會改變。寫法照第二節「數字變數怎麼寫」，寫感受與傾向。文字變數的範圍說明留空。需要負值時（欠費、赤字）把 `min_value` 改成負數。
5. 文字變數的值可以用換行與條列顯示。
6. 官方配方：日期時間、地點、事件摘要三個文字變數放進狀態面板。更新指示用第六節的那一句，不用官方配方的 `[[var:…]]` 格式。
7. 值沒顯示時：狀態面板原樣出現 `{{名稱}}` = 沒有該名稱的變數，檢查名稱；顯示「—」= 值是空的，在作品設定補更新指示；下半被裁切 = 高度超過 300px。
8. MCP 的指南對變數只說「選用，第一版通常 0～2 個」，沒有教怎麼寫，官方細節以 Studio 的說明頁為準。

## 八、模擬器類作品才用
玩家會遇到很多對象、有金錢或資源要結算、角色在遊戲中才生成時才需要。一般的單一角色或少數角色作品跳過這一節。

### 對象格、名冊與隱藏底細
1. **主要格與名冊**：會反覆出現、有好感路線的進主要格（多行，一格一人）；其他人記在一個名冊變數，一人一行。
2. 主要格的欄位分兩種：固定欄位登場時一次生成，之後照抄；會變的欄位（階段、好感、當下動作、心聲）每則更新。
3. **要等條件才揭露的欄位**：在對象進主要格的同一則，就把完整的內容寫進隱藏變數，主要格先寫「？？？」；條件達成時從隱藏變數原樣抄過來，並在隱藏變數那一行標「（已揭露）」。揭露條件用有序列表，一項一個欄位。
4. **握有**：隱藏底細每人加一行，記他手上關於玩家的東西（住址、真名、錄下的檔案、借據）。這一行會變，拿到或失去的那一則改寫；他拿來開條件時照這一行寫。
5. **格子滿了**：新對象先記在名冊；只有玩家用 OOC 指定「誰換成誰」才替換。換下來的壓縮成名冊的一行，行尾留階段與好感，換回來時照這行重建。進出的規則寫在主要格第一格的說明裡，名冊只留自己那一半。
6. 名冊設人數上限，超過時刪掉最久沒出現、關係最淺的一位。

### 帳本與結算
1. 一行放目前持有與待結算，一行放今日收入；每個數字都寫總值。
2. 每筆收入在發生的那一則加進待結算，寫原始金額。
3. 結算綁在絕對日期上（例如每月一號），日期到了的那一則結算一次：照分級表扣一個寫死的抽成金額，剩下的加進總資產，待結算改寫成 0，並把算式寫在通知裡。固定扣款（月租、分期）也掛在某一次結算上。
4. 平台或系統以外收到的錢直接加進總資產；支出在實際付款的那一則扣，可以扣到負數代表欠債。

### 動態角色：用一張通用卡加固定對話格式
適用：作品裡有一群由模型即時生成的角色（領取的對象、路人群、隊員、寵物等），數量、名字、外貌在遊戲中才決定，不能事先一張一張建卡。
1. **建一張通用角色卡**，代表「這一類角色」。`character_intro` 寫這類角色是什麼、資料從哪裡來；`secret` 分三塊：
   - 角色定位：這張卡代表誰；資料來源（對應變數的哪幾格、哪些資料取自其他角色卡的清單），不另行發明。
   - 輸出格式：每次開口或動作前一律標明是誰。固定寫法「名字（必要標籤）: 「…」」，標籤只放玩家需要一眼認出的資訊（例如分類 emoji、等級）。未命名時用固定替代名。多人同場各自分開、各自標名；動作描寫主詞寫清楚，不用「他／她」帶過。
   - 行為準則：態度怎麼隨變數（好感、狀態、階段）改變，說話風格怎麼區分個體，能力與外觀必須與資料一致。
2. **個體資料放變數**（照本節的「對象格、名冊與隱藏底細」），動態角色的資料不寫進作品設定。
3. **格式的版型排在通用卡的「輸出格式」裡**，每一種行各排一行。開場不放有名字的固定角色，用匿名的帳號或未讀通知帶出這類角色，讓模型第一則回覆才生成。
4. 其他角色卡裡若有此類角色的清單，欄位格式要跟通用卡讀取的欄位一致。
5. **原型與生成**：地點章節或作品設定寫原型（身分、癖好、性格、說話方式），不寫性別、名字、外貌；第一次見面時才依配置生成名字與外貌，存進變數鎖定。通用卡的性別留空，頭像用標誌或剪影。
6. **介面型角色**（終端、系統、AI）同理建一張卡：把畫面版型（用程式碼區塊排的樣式與欄位）寫進卡裡，不用設定集關鍵字條目，因為關鍵字太窄會漏觸發、也容易跟作品設定重複。預設語氣與玩家可自訂的風格欄位（寫進介紹頁的玩家模板）都寫在卡上。設定集在這類作品可以是空的。

# 章節

## 這套工作流的做法：章節怎麼用
章節不是用來把主線切成第一步、第二步的。它有幾種用途，一部作品可以只用一種，也可以混用；都用不到的作品不做章節，公開時沒有章節也可以。
- 開局的關係已經寫在公開卡、開場又交代了處境時，不為開局另做一章。
- 只有一章的話，第一個開場會綁在它上面，等於一開場就在那套流程裡，所以只有一套功能流程的作品把流程寫在作品設定。
1. **常見的四種用途**（照作品需要，不限這四種）：
   - 角色一定要等劇情走到後面才揭開的內容（過去的事件、真相、藏起來的身分）。靠章節的切換條件控制何時送入模型；私設寫事件的經過，以及進到這一章後哪個看得見的具體動作發生時說破（不寫模糊時機），角色卡只留它造成的平常反應與怎麼帶開。
   - 特定的功能區塊：會反覆使用、每次照同一套演的流程或場景（分配、結算、評級、抽選、某個固定地點的玩法）。
   - 關卡或特殊事件：只用一次的場合（兩人的某個第一次、告白、求婚、一場任務、一個關卡）。私設第一句寫明這一章只用在哪個場合、結束後照什麼相處（「這一章只用在第一次約會；之後的約會照平常的樣子，不重演第一次的緊張」）；接著寫角色當下的心境與傾向，會因為誰先開口、某個變數狀態而不同的地方分開寫。事件之間各自獨立，條件各自看得見，不必排先後。有這類章節的作品另做一章「平常的日子」，事件過後有地方切回去。
   - 開局：只在一開始成立的設定（起始的處境、資源、難度、多種開局各自的差異）。對話離開這一章之後它就不再送進模型，作品設定只留整場都成立的事。
     - 第一個開場固定綁在第一個章節；有一個以上的開場時，其他開場可以各自選要綁哪一個章節（實測）。草稿裡每個開場有 `startEpisodeId` 欄位，填的是綁定的章節 id，沒綁時是 null（官方指南沒寫這個欄位，要改綁定請使用者在 Studio 做）。開場另外還有 `unlock`、`imageId` 兩個欄位，改開場時原樣保留。
     - 所以預設開局的章節排在第一個；每多一種開局就多一個開場，各綁自己的開局章節。
     - 綁定在 Studio 由使用者操作，我寫完告訴他哪個開場該綁哪一章。
2. **有看得見的入場條件才做成章節**。關卡與特殊事件各有入場條件，可以做；沒有明確入場條件的進展（配角的心結與和解）寫在他的卡裡。
3. 內文只寫「保密」、不列玩家的選項、進行模式用自由移動；標題與切換條件怎麼寫在下面。
4. 一章結束時若留下還沒做完的事（預約、借款、還沒執行的懲罰），指向變數裡的約定清單那一行，跨章節的事才接得起來。

## 流程章節
有些章節是一段流程，不是場景：私設放步驟，切換條件寫「何時切進來」，並寫「寫完回到原本的章節」。

## 官方的欄位與上限
| 欄位 | 上限 | 寫什麼 |
|---|---|---|
| 標題 | 20 字 | 場景名稱 |
| 內文（`body_md`） | 2,000 字 | 本章的情況與壓力 |
| 私設（`secret`） | 2,000 字 | 隱藏情由與揭露速度 |
| 切換條件（`transition_condition`） | 200 字 | 開啟這一章的條件，寫在要進入的那一章上（第一章本來就開啟，不需要）。官方表格寫「切換到下一章的條件」，字面可兩種讀法，但「第一章不需要切換條件」與實測都指向入場條件 |
| 章節數量 | 20 個 | 一部作品可建立的章數 |
- 內文與私設不計入 30,000 字，因為對話中只會載入**目前這一章**；標題與切換條件才計入。
- 官方的分法是內文寫目前情況、私設寫背後情由。這套工作流的做法是內文只寫「保密」，兩樣都放私設（見上方「這套工作流的做法」）。
## 切換條件怎麼寫
- 一句話。雖可寫到 200 字，越長 AI 判斷越模糊（官方 MCP 指南建議 50 字內）。
- 條件裡一定要有 {{user}} 或 {{charN}}。
- 寫具體的行動、選擇、告白、曝光。不加「條件：」前綴。
- 不會切換的條件：「兩人變得親近時」「確認彼此心意」「氣氛成熟時」，沒有判斷標準，AI 無法判斷。
- 會切換的條件：「{{user}} 直接追問 {{char1}} 的謊言」「{{char1}} 把藏起來的文件交給 {{user}}」「{{user}} 選擇獨自前往約定地點」，是否發生一目瞭然。
- 依序進行模式中，第一章不需要切換條件（本來就是開啟的）。
- 「章節無法切換」是最常見的詢問，多半是條件句造成的：先檢查條件有沒有具體行動、有沒有 {{user}}／{{charN}}。

## 進行模式
| 模式 | 運作方式 |
|---|---|
| 依序進行 | 依第 1 章 → 第 2 章順序進行；**一章內對話達 100 次以上，下一章會自動開啟** |
| 自由移動 | AI 依對話脈絡自行往返，不強制順序 |
- 依序進行：有起承轉合、重視順序的故事（相遇 → 親近 → 分離）。自由移動：安排多個場景來回遊玩，或不按章數切分的作品。
- 「章節無法切換」有一半取決於這個選擇。
- 用自由移動時，**標題就是條件**，AI 依標題與內文選擇符合當前情況的卡片，所以標題寫「初次見面」「只剩兩人時」「爭吵之後」，不要寫「第 1 章」。
- 以場景使用時務必設自由移動，否則依序進行 100 次對話後會自動切到不想要的場景。
- 官方的範例：標題「爭吵之後」；內文「兩人提高音量爭吵後的隔天。{{char1}} 裝作若無其事，卻不與對方對視；工作對話簡短而精確。」；私設「{{char1}} 知道是自己先越界，已準備好道歉，卻沒有契機就說不出口。」

## 章節開始背景
Cinema 作品專用，一般 Story 沒有這個欄位（一般聊天的背景由讀者自選）。要從圖庫已上傳的圖片中選；只固定切換到該章後的第一則回覆的背景，之後 AI 依場景選擇，不是鎖定整章背景。留白也可以。
